# 議題: 広告ブロックの今後の作り方と、サポートする Android の範囲

更新日: 2026-11-20。判断のための資料で、決定事項ではありません。決まったら AGENTS.md 第4節「維持すべき技術的決定」を更新します。

## 1. 現状（2026-11-20、bc9e7ef6 時点）

本体（Android System WebView）の広告ブロックは、Yuzu Browser から引き継いだエンジンを拡張したものです。uBlock Origin（uBO）向けのリストを読めるように、uBO の書き方を独自に実装しています。uBO のソースは参照せず、uBO wiki の公開仕様と実サイトの挙動だけを根拠にしています（クリーンルーム、Apache-2.0 を維持、2026-11-19 決定）。

別アプリの `gecko-preview` では、GeckoView に uBO の原本（GPLv3）を同梱して検証しています。本体とは別の applicationId です。

### できていること

- 購読: EasyList、EasyPrivacy、AdGuard Japanese、uBlock filters（既定で有効）。Cookie 同意バナーなどのリストは無効の候補。AdGuard のミラーへの切り替え。
- 通信の遮断: 主要なオプション（domain の entity、denyallow、to、method、redirect と redirect-rule、removeparam と urlskip）。urlskip は主フレームの移動だけが対象。
- 要素の非表示: 通常の CSS と、特殊な要素の非表示（:has-text などの procedural）。
- scriptlet（ページ内の仕掛けを無効にするスクリプト）: 56種類と、その別名。信頼できるリスト限定の trusted 系を含む。
- 実リストでの破棄行（読めずに捨てる行）:
  - uBlock filters: 23,710行中672行（2.8%）
  - EasyList: 77,942行中26行
- 実サイト: やらおん！・オタコム・はちま起稿で、広告なし・誤遮断なし。はちま起稿では Ad-Shield 型の広告ブロック検知も止められている。

### できていないこと（uBlock filters の破棄行の主なもの）

| 内容 | 行数 | 理由 |
|---|---|---|
| 代替スクリプト（google-ima.js・fuckadblock.js 等）への置き換え | 193 | uBO wiki に動作の説明がない |
| csp（ページのスクリプト実行を禁止する） | 65 | WebView では応答ヘッダーを変えられない。meta 要素を差し込めば一部はできる可能性がある |
| header・replace（応答ヘッダー・本文で判定・書き換え） | 34 | WebView の要求の横取りでは応答を書き換えられない |
| popunder | 23 | 裏で開くウィンドウを区別する手段が限られる |
| 個々には対応しているオプションの組み合わせ | 61 | 調査が必要 |
| HTML フィルタ（`##^`）の一部 | 49 | script:has-text 以外の形 |
| wiki に説明がない scriptlet（nobab・popads-dummy・trusted-create-html 等） | 約60 | クリーンルームの根拠がない |

確認の範囲は、日本の3サイトと計測テストだけです。海外の動画サイトや、ログインが必要なサイトでは確かめていません。

## 2. 保守性の課題

- **uBO の更新に追いつく必要がある**: uBO には、新しい scriptlet や書き方が頻繁に加わります。リスト（uAssets）はすぐに新しい書き方を使い始めるので、追従しないと破棄行が少しずつ増え、広告が漏れたりサイトが壊れたりします。
- **wiki が実装に遅れることがある**: 見出しだけで本文がない節（trusted-replace-fetch-response）や、節自体がないもの（trusted-create-html）があります。そのような場合、クリーンルームの方針では推定で作るか、作らないかの二択になります。
- **細部の違いに気づきにくい**: 互換実装の差は、特定のサイトで初めて表に出ます。確認できる範囲には限りがあります。

## 3. 選択肢

| 案 | 内容 | 利点 | 欠点 |
|---|---|---|---|
| A. 現状の方針を続ける | wiki を根拠に、独自の互換実装を追加していく | Apache-2.0 のまま。WebView のまま、本体に統合できる | 追従の作業がずっと続く。部分的な互換にとどまる |
| B. A＋代替スクリプトを公開 API 文書から作る | Google IMA・GPT 等の公開 API 文書を元に、無害な偽物を独自に作る（承認済み） | 193行が減り、動画サイトの「広告ブロックを解除して」が減る見込み | 各ライブラリの API が変わったら直す必要がある。どこまで作るかの線引きが要る |
| C. 対応範囲を絞る | EasyList・AdGuard JP を中心に、uBO 独自の書き方は効果の大きいものだけにする | 保守の負担が最も小さい | 動画サイトや広告ブロック検知への対策は弱くなる |
| D. 本体を GPLv3 にして uBO の資源を取り込む | uBO の scriptlet と代替スクリプトを、そのまま同梱・同期する | 互換性が最も高く、追従は同期で済む | アプリ全体のライセンスが GPLv3 に変わる（Yuzu の Apache-2.0 コードとは組み合わせられる）。2026-11-19 の決定を覆すことになる |
| E. 本体の表示エンジンを GeckoView＋uBO 原本にする | gecko-preview の路線を本体へ広げる（engine-api の方向） | uBO の機能をすべて使える。拡張機能も動く | APK が大きくなる。WebView 前提の機能を移す作業が大きい。minSdk 26 以上が必要 |
| F. 外部の広告ブロックエンジンを使う | 例: Brave の adblock-rust（ライセンスは要確認）を NDK で組み込む | 照合部分の保守を外部に任せられる | ライセンス、とくに scriptlet 資源の出どころの確認が必要。Rust のビルドを Docker に入れる必要がある |

### 提案

短期は B（効果の大きい代替スクリプトだけ）を進めます。ただし、「追従の作業を減らす」という目的にはならないので、中長期の方針（A・C・D・E のどれに寄せるか）を別に決めるのがよいと考えます。

- 互換性を最優先するなら、D か E
- ライセンスと WebView を最優先するなら、A か C

F は、ライセンスの調査結果次第です。

### 決定（2026-11-20）

当面は B 案で進める（利用者の承認）。他のブラウザの方式と今後のリスクを考慮しながら進める。

### 他のブラウザの方式と、今後のリスク（2026-11-20 の調査、詳細はローカルのレポート reports/adblock-browsers-survey-2026-11-20.md）

- Firefox・Edge（Android）: uBO の原本を拡張機能として使い、本体とは分けている。E 案に近い形。
- Brave: エンジンは adblock-rust（MPL-2.0）、資源集は adblock-resources（MPL-2.0）。資源集の README に uBO 由来の資源の区分があり、GPLv3 との整合のさせ方は未確認。
- Samsung Internet: 外部アプリがブラウザ側の Content Blocking API を使う方式で、複雑なルールは使えない。Vivaldi は内蔵の遮断（実装の詳細は未確認）。
- Yuzu Browser・BerryBrowser: 内部の実装は公式の資料に届かず、未確認。
- AdGuard Scriptlets: GPL-3.0。Apache-2.0 でも提供しているという報告があるが、根拠が EULA の記載だけのため要確認。
- Apache-2.0 の本体に uBO の GPLv3 資源を混ぜた例は見つからなかった。B 案のように、独自に書いて出どころを記録する方式は、他社の実情と矛盾しない。

今後のリスク（上位）:

1. ライセンス: 代替スクリプトを作るときは、参照した公開 API 文書の URL と日付を記録し、uBO の資源を見ながら書かない。
2. 法的な動向: ドイツの Axel Springer 対 Eyeo 訴訟は、2025年8月に連邦通常裁判所（BGH）が著作権に関する判断を差し戻した。2026年の差戻し審の結果は未確認で、今後も注視する。
3. 反広告ブロック: YouTube 型の検知は更新が続き、恒久的な回避策はないとされる。応答を書き換えられない WebView 本体は構造的に不利なため、YouTube 型と Ad-Shield 型は B 案の成功条件に含めない。
4. Google Play: 「他のアプリの広告を妨げる」行為の禁止は、ブラウザ内の遮断には及ばないと読むのが通説。ただし公式の明言は確認できていない。
5. リストの配布: EasyList は GPLv3 以降と CC BY-SA の二重、AdGuard の各リストは GPL-3.0。同梱すると条件（帰属表示・同一条件）が及ぶため、現状どおり実行時に購読して取得する方式を続ける。uAssets・Fanboy のリストの正確なライセンスは未確認。

B 案への示唆: 対象は、効果の大きい数種（IMA・GPT 等）に限る。追従の作業を減らす効果は薄いため、中長期は C 案（範囲を絞る）か、E 案（GeckoView＋uBO 原本の併用）を検討する。

## 4. 関連する議題: サポートする Android の範囲（minSdk）

現在は minSdk 23（Android 6.0）です。AndroidX WebKit は 1.16 以降で minSdk 24 が必要になり、今回は 1.15.0 で止めています。

| 案 | 利点 | 欠点 |
|---|---|---|
| 23 を維持 | 古い端末の利用者を切らない | AndroidX の新機能（WebKit 1.16 以降の API 等）が使えない。古い OS での確認の負担が残る |
| 24 に上げる | WebKit の最新版（1.18 系）を使える。差は小さい | Android 6.0 の端末を切る |
| 26 に上げる | GeckoView（E 案）と揃う。古い OS 向けの分岐を減らせる | Android 7.x の端末も切る |

判断材料として、Android 6〜7 の利用者の割合（公開統計）と、Yuzu Browser の利用者の端末の傾向を調べる必要があります。どちらも未調査です。

## 5. プライバシー機能と利便性

新しいプライバシー機能は、既存の利便性を損なわないよう、初期値はオフ、またはサイトごとの選択にしています。

- **サイトのデータの消去**（ページ情報から手動、またはタブを閉じたら自動）
  - 自動消去は、利用者がサイトごとに選んだ場合だけ動く。同じサイトのタブがほかに開いていれば消さない。
  - 消えるのは Cookie・保存データ・キャッシュで、そのサイトからはログアウトされる。
  - 後で読むの保存ページ（アプリ内のファイル）、閉じたタブの復元、ブックマーク、履歴は消えない。ただし、復元したタブはログアウトした状態で開く。
- **リンクを対応アプリで開く**（初期値オン）
  - Chrome と同じく、既定のアプリがあるリンクはアプリで開く。設定でオフにできる。
- **Cookie 同意バナーなどのリスト**（初期値オフ）
  - バナーを消すとき、サイトの既定の扱い（同意または拒否）になる場合がある。利用者が選んで有効にする。

今後のプライバシー機能（自動消去の拡大、プロファイル分離など）も、タブの復元・後で読む・ログイン状態の維持を壊さないことを条件にします。
