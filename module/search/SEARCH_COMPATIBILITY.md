# 検索設定と画面の互換性

Google は国別ドメインから google.com への統一を[公式に案内](https://blog.google/products-and-platforms/products/search/country-code-top-level-domains/)しているため、新規設定には `https://www.google.com/search?q=%s` を使用する。

保存済みの全体検索URLは、過去に配布した2種類の初期URLとの完全一致だけを移行する。検索プロバイダーは初期GoogleのID・名称・色・ファビコン設定も一致する場合に限って移行し、選択ID・採番・順序を保つ。独自URLや追加パラメーター、編集済みの項目は変更しない。初期値と同じ文字列をユーザーが手入力した場合は区別できない。プロバイダーのJSONキーと保存先は従来のまま、書き込みは `AtomicFile` で保護する。

通常起動と設定の取り込み後には `SearchDefaults.migrateLegacyDefaults(context, moshi)` を共用する。全体設定の正規化は既存の `AppPrefs.load` が担当し、検索ファイルの正規化によって全設定を再保存することはない。

検索語はUTF-8で符号化して最初のプレースホルダーへ挿入する。アドレス入力では、既存のURL判定・スキーム・裸のドメイン名の補完を維持する。Google候補の要求には `q` を使う。候補取得はネットワークや相手側の提供状態に依存するため、固定応答を読むテストと実際の候補表示は分けて確認する。

画面は [Material Components 1.14.0](https://github.com/material-components/material-components-android/releases/tag/1.14.0) のMaterial3 Viewsを使用する。既存のテーマ名・toolbarの配置/高さ・アクションID・ジェスチャー・設定キーを維持し、アドレス欄とメニューの形状/余白、設定の文字組み、検索の入力欄/ダイアログを更新する。独自テーマの明示文字色・押下色・メニュー文字サイズを優先し、Dynamic Colorsによる自動上書きは行わない。

回帰テストは旧seed/独自設定/JSONの保持、日本語・記号の符号化、候補URLと固定応答、実AndroidのURL判定とAtomicFile復旧、入力フォームの生成を対象にする。ビルドと端末での実行結果は進捗の記録へ別途記録する。全レイアウト・全操作・全OSでの実描画を保証するものではない。

## 旧バックアップからの検索項目の統合

`SearchImport` は旧Yuzu 6.0.2と同じ既知形式の `files/searchUrl.json` を扱う。任意クラスのデシリアライズやファイル書き込みは行わない。UTF-8・JSONの重複キー・末尾・階層を検証し、入力2MiB、文字列64Ki文字、検索項目1024件までに制限する。不正な入力や統合結果が上限を超える場合は適用前に失敗させる。

統合では現在のCitrusの項目・ID・順序を保持する。取込元と名称/URL/色/ファビコン指定がすべて同じ項目は再利用し、それ以外は取込元の順で末尾へ追加する。衝突したIDだけ採番し直し、元のIDと結果のIDの対応表を返す。旧Googleの初期値はIDを変える前に正規化する。独自URLの追加パラメーターは変更しない。

取込元の有効な選択IDは対応表で移し替える。旧初期値の選択ID `0` に対応する項目がない場合は、旧実装と同じく取込元の先頭項目を選ぶ。それ以外の存在しないIDを表示位置と推測して読み替えず、現在の選択を維持する。空の取込一覧でも現在の項目と選択を保持する。検索画面の選択位置を保存する場合も、indexではなくその項目の安定したIDを保存する。

JSONの選択と全体設定の `search_url` は旧実装から別の値である。全体URLは設定XMLを選んだときの移行規則に従い、検索項目の統合だけで別の全体URLを書き込まない。確認後の適用では `decode` → `merge` → `encode` の結果を既存の取り込みトランザクションへ渡し、現行ファイルが破損していれば空一覧として上書きしない。書き込みの失敗は他カテゴリと同じ復旧手順で扱う。

旧Yuzuの設定画面は追加した検索項目を採番せず `-1` のまま保存する場合がある。この既知の仮IDだけは重複を拒否せず、他のIDへ衝突しない固有IDに直す。選択も `-1` の場合は従来の最初の一致を維持し、個々の独自URL・順序・色を保持する。通常読込でも同じ補正を使い、今後の新規追加はモデルの採番処理を通す。正のIDの重複など、別の不正構造まで推測で修復しない。

編集画面は保存成功時だけ未保存フラグを解除する。未保存の編集がなければ再開時に外部変更を再読込し、古い画面を再び閉じただけで取り込んだ一覧を上書きしない。IO失敗時は編集中の一覧をメモリに残す。その間に別の取り込みが完了した場合は元の読込内容との差を検出して自動保存を中止し、ディスク上の新しい項目を保護する。これは同時編集を完全に統合する仕組みではなく、未保存内容はプロセス終了を越えて保証しない。通常の検索画面で検索エンジンを切り替える経路も、保存時の最新一覧へ選択IDだけを反映する。
